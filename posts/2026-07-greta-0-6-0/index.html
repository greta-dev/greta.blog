greta 0.6.0

greta 0.6.0 is back on CRAN, with a ground-up rebuild of the Python installation experience: uv-managed and automatic, works offline, and lets you choose your backend with greta_set_python() and greta_set_deps().

We are delighted to announce the release of greta 0.6.0. greta lets you write statistical models directly in R and fit them with MCMC, using TensorFlow and TensorFlow Probability to do the heavy lifting.

install.packages("greta")

greta was archived from CRAN in late 2025, so the headline news is simply that it is back. Getting there meant rebuilding how greta manages its Python dependencies, which is the bulk of this release. You can see the full list of changes in the release notes.

The short version

  • greta 0.6.0 is on CRAN again.
  • The Python dependencies are now installed automatically via uv on first use, so install_greta_deps() is no longer a required step for most people.
  • It works offline. Once uv’s cache is populated, greta can start up without an internet connection.
  • You can choose your Python backend, persistently, with greta_set_python(), and pin your dependency versions with greta_set_deps().
  • mcmc() now defaults to two chains on two cores, where it previously used four chains. If you relied on the old defaults, set them explicitly.
  • A scattering of removal and reinstall helpers have been consolidated behind greta_remove() and reinstall_greta_deps().

Because greta is back, its three extension packages can return to CRAN too. greta.gp and greta.dynamics are already there, both at version 0.2.3, and greta.gam is on its way.

Why greta was archived

greta sits on top of TensorFlow and TensorFlow Probability, which are Python libraries. You can think of them a little like highly optimised linear algebra engines: they are a big part of what makes greta fast and expressive, and they are how greta fits MCMC efficiently. But they also mean greta has to manage a Python installation, and getting the right combination of package versions in place has been a genuinely hard problem.

That caused two problems on CRAN. greta used more than two cores by default, and it could reach out to install TensorFlow and TensorFlow Probability onto the machine running the checks. Both come back to the same underlying issue: managing greta’s Python dependencies well.

Previously, we leaned on conda and a curated table of “known good” version combinations. The install_greta_deps() function did a good job of setting all of this up, most of the time. When it worked, it was lovely. When it did not, installation could get complicated quickly.

More recently, reticulate gained a fast new environment manager built on uv, which changes what a good installation experience can look like. Rebuilding greta’s installation around it is the heart of this release.

Installation that just works

greta now installs TensorFlow and TensorFlow Probability automatically via uv the first time you use it. You no longer need to run install_greta_deps() as a separate step before you can build a model:

library(greta)

# on first use, greta sets up its Python environment for you
x <- normal(0, 1)
m <- model(x)
draws <- mcmc(m, n_samples = 100)

Just as importantly, greta is now flexible about which Python environment it uses. Instead of always forcing one managed environment, greta resolves its backend in order:

  1. a user-set RETICULATE_PYTHON,
  2. a stored greta preference (see below),
  3. an existing greta-env-tf2 conda environment,
  4. otherwise, the managed uv environment.

So you get convenience by default, without giving up control.

Choosing your Python backend

greta_set_python() records which Python environment greta should use, and the preference persists across sessions. You can pick the managed uv environment, a conda environment, or a specific Python:

# the default: reticulate's managed uv environment
greta_set_python("uv")

# an existing conda environment
greta_set_python("conda", name = "greta-env-tf2")

# a specific interpreter, or an environment directory
greta_set_python("path", path = "~/.virtualenvs/greta/bin/python")
greta_set_python("path", path = "~/.virtualenvs/greta")

That last pair is worth calling out: greta_set_python("path", ...) accepts either a Python binary or an environment directory (a virtualenv or conda prefix), looking for bin/python (or Scripts/python.exe on Windows) inside it. This makes pre-installed and offline setups easier to wire up.

Each call reports the preference it stored, warns you if RETICULATE_PYTHON will take precedence over it, and shows what greta will resolve to on its next load. To clear the preference and go back to automatic resolution, use greta_reset_python().

Offline support

The managed uv backend now works without an internet connection. Once reticulate’s uv cache is populated, greta enables uv’s offline mode, so it can start up on a plane, behind a locked-down corporate firewall, or on an air-gapped compute node.

If you want to be explicit, set the UV_OFFLINE environment variable to force the behaviour you want:

# force offline resolution
Sys.setenv(UV_OFFLINE = 1)

# force online resolution
Sys.setenv(UV_OFFLINE = 0)

Pinning your dependency versions

greta_set_deps() persistently pins which TensorFlow, TensorFlow Probability, and Python versions greta should use. The managed environment installs them on next load, and install_greta_deps() picks them up as its default:

greta_set_deps(
  greta_deps_spec(
    tf_version = "2.15.1",
    tfp_version = "0.23.0",
    python_version = "3.11"
  )
)

Clear the pins with greta_remove("deps").

greta_deps_spec() is also less rigid than it used to be. It no longer validates every requested combination against a fixed compatibility table. It now checks only that the requested TensorFlow version is one greta supports, and leaves the rest for uv or conda to resolve. Fewer surprises, and less maintenance of a table that goes stale.

NoteTwo different TensorFlow versions

greta depends on the R package tensorflow, and separately on the Python library TensorFlow. These are versioned independently, and 0.6.0 changed both.

greta’s DESCRIPTION previously required the R package at exactly == 2.16.0, which is brittle by design; it now accepts >= 2.16.0.

The Python library is a different story: greta supports Python TensorFlow up to 2.15.x. TensorFlow 2.16 and later ship Keras 3, which greta does not yet support, so greta_deps_spec(tf_version = "2.16.0") will tell you so rather than installing something that will not work.

Seeing what greta will do

greta_sitrep() has grown to match all of this. It reports the resolved Python backend and whether greta can start offline, including the UV_OFFLINE setting and whether the uv cache is populated, so you can see at a glance what greta will do on its next load. A missing conda environment is now reported neutrally as “not used” on the uv backend, rather than as a failure.

It also gains a verbosity argument, with three levels of detail:

greta_sitrep()                          # "minimal", the default
greta_sitrep(verbosity = "detailed")    # everything
greta_sitrep(verbosity = "quiet")       # just the essentials

If you are debugging a conda setup, greta_list_py_modules() shows the Python packages installed in a given TF2 environment.

Lifecycle changes

We consolidated a scattering of removal and reinstall helpers. greta_remove() is now the single front door for cleaning up. One what argument covers every case:

greta_remove("env")         # the greta-env-tf2 conda environment
greta_remove("miniconda")   # miniconda
greta_remove("uv_cache")    # reticulate's uv cache
greta_remove("preference")  # your stored Python preference
greta_remove("deps")        # your stored dependency versions
greta_remove("all")         # all of the above
  • Superseded by greta_remove(): destroy_greta_deps(), greta_remove_all_deps(), remove_greta_env(), remove_miniconda(), and remove_reticulate_uv_cache().
  • Deprecated in favour of reinstall_greta_deps(): reinstall_greta_env() and reinstall_miniconda().
  • Behaviour change: n_cores now defaults to 2 and chains defaults to 2. If you ask for more cores than you have, greta uses what is actually available. This keeps greta polite on CRAN’s two-core check machines, and on laptops. If you were relying on the old default of four chains, pass chains = 4 explicitly.

greta_remove() also no longer leaves a stale, deleted environment active for the rest of the session. It invalidates greta’s cached Python backend and nudges you to restart R, instead of silently failing or reporting the removed environment as still available. The older remove_*() functions now ask for confirmation before removing, gain an ask argument (defaulting to interactive()) so they work in scripts, and invisibly return whether anything was actually removed.

One note on remove_reticulate_uv_cache(): that cache is shared by all reticulate packages and is not greta-specific. A system-wide uv cache is left untouched.

Other changes

A few smaller things make everyday modelling nicer:

  • Clearer MCMC output. The MCMC print method now includes warmup information.
  • Better display of unknown dimensions. Reshaping a greta array with dim<- keeps the familiar ? placeholder for unknown values instead of showing NA.
  • outer() works. outer() (and %o%) now works with greta arrays when FUN = "*", instead of silently returning a base array of NAs. Base R’s fast path for "*" used as.vector(), which dropped the greta operation.
  • log() warns about base. log() on a greta array now warns when the base argument is supplied, as it was being ignored.
  • Silenceable notes. Notes are now emitted with message() rather than cat(), so you can wrap them in suppressMessages().
  • Assorted fixes. as.unknowns() now handles plain numeric vectors, library(greta) no longer errors when the stored Python preference file exists but is empty, install_greta_deps() records where it put the greta-env-tf2 conda environment so greta can find it in any conda installation, and greta_sitrep() now requires Python 3.9 or later.

What this means for you

If you are a returning greta user: your models are safe and the API you know is intact. The biggest practical change is that getting greta running should be much less fuss than it used to be, and that mcmc() now runs two chains by default rather than four. If installation ever misbehaves, greta_sitrep() will tell you what greta sees and what it will do next.

If you are new to greta: welcome! You can install it straight from CRAN, and the Python side of things should sort itself out on first use.

install.packages("greta")
library(greta)
